# 视觉分析持久任务与恢复

照片接收、结果事件审计和 vision_job 入队在同一个 MySQL 事务提交后，才对机器人返回应用确认。服务重启不依赖内存线程池中的任务列表。

## 执行与提交

启动后创建两个分析 worker，每次通过 FOR UPDATE SKIP LOCKED 领取一条到期任务。领取生成随机 lease_token，并写入 60 秒租约，每 15 秒续租。调用 VLM 时不持有数据库锁。结果返回后，只有租约未过期且 token 仍匹配的 worker 可以提交。

结果、告警变更与 job 的完成状态在同一个事务提交。任务以 (task_no, point_seq) 唯一，重复照片和重复完成不会重复生成告警；失去租约的旧 worker 也不能覆盖新结果。数据库提交失败时保留未完成租约，后续可重新领取。

正常停机会释放已知任务的租约；强制终止进程后，其他 worker 在最后一次续租后的 60 秒内接管。外部模型请求可能执行不止一次，因此不承诺模型 API 恰好调用一次；保证业务结果和告警不会因重放重复提交。原始图片仍依赖配置目录的持久保存，数据库队列不能恢复被删除的图片文件。

## 重试边界

每个任务最多领取执行 3 次，调用失败后分别等待 10 秒、30 秒再重试。既有 VLM 客户端每次最多两次 HTTP 调用，最多可能产生六次模型请求。进程中断也消耗一次执行预算；连续中断耗尽预算后结束为失败，进入人工复核。

调用失败的中间状态不写最终检测结论，也不提前生成告警。三次耗尽后写入失败结果并生成设备待复核事项。正常、异常和“看不清”都是完成的检测结论：“看不清”进入复核，不反复请求模型碰运气。

检测记录显示等待分析、正在分析、等待重试、自动分析已停止，以及已尝试次数。成功与失败均保留数据库执行状态和最后错误，失败后可人工复核或重新发起巡检。

## 升级与运维

增量迁移 005_vision_jobs.sql 自动建表。启动时扫描有照片且尚无 inspection_result 的历史 result_received 事件，按冻结的任务规则补入队列；不重新分析已有正常、异常、待复核或失败结论。历史空图像不入队。已存在的队列任务通过唯一键保持幂等。

诊断 SQL：

~~~sql
SELECT status, COUNT(*) FROM vision_job GROUP BY status;
SELECT task_no,point_seq,status,attempts,last_error,available_at,lease_until
FROM vision_job ORDER BY id DESC LIMIT 50;
~~~

## 验证

74 项隔离 MySQL 后端测试通过，包括照片接收回滚、并发领取、租约过期接管、旧 token 拒绝提交、续租、退避、三次耗尽、冻结规则、告警与结果原子提交、升级补漏和正常停机。

独立进程验收会终止分析中的 worker，再启动新进程，实际等待租约到期后接回任务，验证 attempts=2、结果一条、告警一条、旧 token 提交被拒绝。脚本 backend/scripts/vision_recovery_acceptance.py 使用独立测试数据库并自动清理。为缩短测试，租约设为 2 秒；模型返回是确定性测试替身，不代表视觉准确率。详见 [验收记录](validation/vision-recovery-acceptance.json)。

前端构建通过，仍保留现有的大包体积提示。

升级后的本地页面已验证等待重试与停止状态。自动补做的一张早期历史照片因文件已不存在，三次后结束为失败，保留错误供人工检查；本次没有新增巡检任务，原 30 条任务保留。
