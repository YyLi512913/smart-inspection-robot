# 项目描述与面试讲述提纲

定位：机器人应用后端与 ROS 2 上层集成的工程项目。以下是项目能力描述和简历表述参考，个人职责、开发周期、协作方式按实际情况填写；本资料不代填工作经历或个人贡献比例。

## 一分钟介绍

“巡境是一个设备级机器人巡检工作台。我关注的是机器人上层业务系统怎样可靠地执行任务并处理异常：操作员选择设备后，后端校验续航和占用，通过 MQTT 下发给 ROS 2/Nav2 执行端，到点停稳采集图像，再进入视觉分析与人工复检闭环。

项目把任务与指令放在同一数据库事务中，机器人端用 SQLite 保留执行与补报记录；视觉分析也使用持久任务和租约恢复。当前有登录权限、审计、运行状态和统一验收。验证环境是 Gazebo，尚未上真机，也不把少量仿真照片的通过当作工业识别准确率。”

## 简历项目栏参考

**巡境 · 机器人设备巡检与异常闭环系统｜个人工程项目 / 仿真验证**

Python、FastAPI、MySQL、Redis、MQTT、SQLite、ROS 2、Nav2、Gazebo、Vue 3。

- 构建设备台账、观察点和规则快照，串联任务创建、续航校验、Nav2 导航、到点拍照、视觉分析和异常复检，支持结果按设备与任务追溯。
- 通过 MySQL 事务发件箱、指令/事件幂等、机器人 SQLite 补报及取消确认机制，处理重复消息、断连和恢复；视觉任务使用租约和有限重试，避免旧 worker 覆盖结果或重复产生告警。
- 接入登录角色、服务端身份审计、运行状态、同源部署及统一故障验收；最近完整批次通过 117 项后端和 9 项 ROS 组件测试，另保留实际 Gazebo 相机及模型联调证据。

篇幅有限时可压缩为：

“基于 FastAPI、MySQL、MQTT 与 ROS 2/Nav2 实现单机器人设备巡检应用，覆盖设备规则、任务可靠下发、持久视觉分析及人工复检闭环；通过事务发件箱、幂等与 SQLite 补报处理断连/重启，配套权限、审计和故障验收。项目在 Gazebo 验证，尚未部署真机。”

使用描述时应选取自己实际理解和承担的部分。AI 辅助生成过的实现，也应能结合代码说明状态、失败路径与测试依据；不需要把未使用的框架写进技术栈。

## 一个值得复盘的失败案例

首轮管路异常识别漏检：积液视野被裁切、几何表达不清。保留原记录，调整观察距离和场景几何后重新采集，之后检出异常。柜门开启仍存在漏检，控制柜异常主要由红灯被检出。

可讲清楚的改进是“用失败样本定位采集与场景表达问题，并重新验证”，而不是“已达到某个准确率”。后续应建立多角度、光照、遮挡样本及误报漏报指标。见 [原始失败记录](validation/equipment-first-pass-missed-leak.json)。

## 面试前自查

能从一个具体任务解释：谁创建、设备和规则如何确定、指令何时提交、重复指令如何处理、机器人何时允许拍照、图像失败如何表示、分析何时恢复、告警何时关闭。

再挑三个失败点，说明已有处理和仍需人工介入的边界，例如取消状态不确定、图片文件丢失、模型读不清。个人负责部分要能定位到对应代码和测试，不把项目总体功能当成未经确认的个人工作量。

演示顺序见 [录屏脚本](demo-guide.md)，完整实现说明见 [架构文档](architecture.md)。
